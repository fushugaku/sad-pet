# Wavetable: фон, память и сохранение звука

31 октября — 1 ноября 2026. Цель: существующий Rack, четыре ноты `[48, 51, 55, 58]`, четыре разные комплексные 64-frame таблицы, Unison 4, все четыре linear FM и все четыре hard sync одновременно. Источники образуют два независимых кольца. [Точный патч](../wasm-unison4/target-preset.json).

## Проверка опубликованной сборки — текущий статус

[CI и публикация](deployment.json): релиз `c716815`, все проверки CI прошли. Публичный SIMD SHA-256 — `d86c66f654829dd71df4b7d7b37ec03ec24470f74594fd5a4ee2421e9555cafa`. Его PCM побайтово совпал с локальным релизом во всех 21 сценарии; сравнение с прежним публичным релизом также прошло 21/21. Память полного публичного приложения — **127.240 MiB maximum**, в пределах 128 MiB.

**Realtime gate в текущих условиях не пройден.** [Публичный iframe-прогон](app-public-loaded-stopped.json), [контрольный локальный](app-local-battery-stopped.json) и [опубликованный bundle в основном документе](app-top-level-battery-stopped.json) показали массовые underrun. Тесты остановлены; ни один не считается PASS. Сейчас Mac питается от батареи, `ProcessInfo.isLowPowerModeEnabled == true`; одновременно наблюдалась сторонняя вычислительная нагрузка. Режим питания и чужие процессы не менялись. Это наблюдение условий, а не доказательство единственной причины. Предыдущий локальный 10-минутный PASS сохранён ниже; он не подменяет последние неудачные проверки.

[CPU опубликованного модуля под текущей нагрузкой](cpu-deployed/comparison.json): основной render p50 **3.651 → 3.674 ms**, пары **4.051 → 4.259 ms**, движение Position **4.026 → 4.050 ms**. Абсолютные числа выше прежнего измерения; universal deadline gate не закрыт. [Восемь preset edits](cpu-edits-deployed/comparison.json): медиана **523.980 → 75.034 ms (−85.7%)**, 32 → 0 компиляций и 144 970 784 → 0 переданных bytes.

Отдельно учтено, что [Chromium выбирает SemiRealtimeAudioWorkletThread для iframe](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/webaudio/audio_worklet_messaging_proxy.cc), а RealtimeAudioWorkletThread — для основного документа. Контрольный top-level прогон исключил только эту переменную; перегрузка в текущих условиях сохранилась. Требуется определить целевой режим питания перед дальнейшим performance gate.

## CPU и звук финальной сборки

Baseline — публичный релиз `39e65e65385dd96285e750d052c36b07c80d912c`, SIMD SHA-256 `3d873bcc21ecdf5f7475bab87623ad0519cb233d4c6537f54c63ebc55dcbe8be`. Измеренная новая SIMD-сборка: `39623603e9c4034d7540e36902161709a75c1255ed2c89b968082a54b3543e30`.

Apple M5 Max / arm64, Node 24.19, 48 kHz / 128 frames. [CPU AB/BA](cpu-ship/comparison.json): по два отдельных прогона на версию/сценарий, каждый с 1 s audio warmup и 4 s измерения, 3000 измеренных блоков на версию/сценарий. Банки перед измерением подготовлены utility и помещены в realtime arena, как в AudioWorklet (`WT_PREPARED=1`); realtime ROM reads равны нулю. Подготовка и controls исключены из интервала render CPU.

## Что изменено

- Неизменённые gzip-данные всех 96 заводских таблиц перенесены из linear memory каждого экземпляра в custom sections общего скомпилированного WASM-модуля. Worker извлекает одну таблицу по запросу. В аудио-экземпляре разрешаются только заранее подготовленные банки; render не вызывает ROM imports. Factory IDs, canonical float32, content hashes и размер таблиц сохранены.
- Начальный аудиорезерв банков — 36 MiB. Он вмещает четыре звучащих 64-frame банка и четыре замены. Дополнительные 28 MiB готовятся при необходимости; исходная общая ёмкость 64 MiB и возможность четырёх 256-frame пользовательских таблиц сохранены. Эта расширенная нагрузка не входит в проверяемый профиль 128 MiB.
- После завершения 20 ms crossfade старые банки возвращаются в резерв на следующем control-side prune. Завершённый fade не удерживает стартовую волну перед очередной заменой четырёх банков.
- При смене банков без звучащих голосов переход завершается сразу. Раньше первый аккорд ещё 20 ms смешивался с несыгранной Basic Morph, что переводило весь четырёхоператорный граф на медленный путь. Плавная смена банков у звучащих нот сохранена. Это намеренное исправление атаки после тихой замены: при одинаковых controls новый первый аккорд совпадает побайтово с запуском сразу выбранного пресета; живая смена банков входит в прежнюю PCM-матрицу.
- Worker повторно использует буфер компилятора. Новый ABI отдаёт небольшой заголовок и view готовых float32; JS собирает существующий переносимый пакет напрямую. Отдельной полной PCM-копии внутри WASM больше нет. Старый packed ABI сохранён; регрессия сравнивает пакеты побайтово после компиляции разных волн.
- Повторная установка пресета сначала проверяет реальные банки аудио-экземпляра по header/hash/revision. Неизменённые волны не компилируются и не передаются повторно. Новый аудио-экземпляр требует повторной загрузки: кеш заголовков в JS не считается доказательством наличия банка.
- Vocal создаёт WASM только при первой реальной Vocal-команде. Пустые jobs и clock updates его не запускают. Запись не создаёт дополнительный WASM-экземпляр.
- `?engine=wavetable` запускает Wavetable Rack сразу, без предварительного разворачивания sample/FX-сцены Glasses 5. Обычный маршрут и сохранённые sample-сцены остаются доступны. Этот профиль памяти требует прямого WT-старта: уже выросшая linear memory после тяжёлой sample-сцены не уменьшается при смене инструмента.
- До создания живого worklet utility прогревает тяжёлый четырёхголосный FM/sync-граф и binary snapshots на общей `WebAssembly.Module`, затем полностью сбрасывает состояние. Ноты прогрева не попадают в аудиовыход. Старый Registry освобождается до создания нового, без одновременного удержания двух полных сцен. В diagnostics записаны frames, snapshots, peak, время и high-water прогрева.
- `resume()` возвращает общий promise запуска AudioContext. Первые MIDI/keyboard note-on и note-off сохраняют порядок и ждут завершения resume; первый аккорд не отправляется в ещё запускающийся поток. Публикация состояния также прогрета до живого воспроизведения.
- SIMD renderer использует известные границы фаз и пропускает ненужный `floor` только на безопасном пути. Последовательность 32 сложений master-clock в f64 сохранена. FIR folding применяется только при точной симметрии коэффициентов. Feedback taps сохраняют прежний порядок; остальные случаи используют исходный путь.
- `AudioContext` запрашивает `latencyHint: 0.01`. На проверенном устройстве base latency меняется с 5.333 до 10.667 ms. Это запас против scheduling jitter, с измеримым увеличением задержки. Частота устройства и 128-frame quantum не меняются.

Сохранены 8× FM/PM, 32× sync, f64 phase, sinc16, polynomial degree 7, BLEP/BLAMP и FIR 63/641 taps. Oversampling, полифония и число unison lanes не сокращались.

## Что именно считается памятью

128 MiB = 134 217 728 bytes. Это бюджет **аудиоданных**, а не RSS процесса браузера:

1. Полные `memory.buffer.byteLength` всех реальных WASM-ролей: AudioWorklet, utility, telemetry, Vocal, recorder. Включены начальные выделения, свободное пространство внутри выросшей linear memory и staging high-water.
2. Общий lossless factory ROM и metadata custom section, посчитанные один раз.
3. Самый большой передаваемый bank packet.
4. Три snapshot-буфера по максимальной ёмкости и recording pools worklet.

DOM, JS-объекты метаданных, машинный код, браузерные wire/code caches и прочие вкладки сюда не входят. Отчёт не утверждает, что весь процесс браузера помещается в 128 MiB. Скомпилированный модуль передаётся worker-ролям как `WebAssembly.Module`; использование общего compiled module соответствует [модели V8](https://v8.github.io/api/head/classv8_1_1CompiledWasmModule.html). Извлечённые custom-section bytes временные; готовые пакеты передаются через transfer list.

`GET /api/diagnostics/memory` показывает все роли, ROM, максимальный transfer, playbackStats, latency, контекст, звучащие ноты и конфигурацию WT. В utility сохраняется ограниченная история команд, увеличивших linear memory. Это диагностика между render calls.

## Как проверяется

- `wasm/test-wavetable-memory.mjs`: production worker protocol и настоящие WASM-экземпляры. Сначала стартовая Basic Morph, запросы браузера таблиц, затем полный четырёхволновый патч; telemetry snapshots 20 Hz, движение Position, проверка неизменной памяти и нулевых ROM reads на аудиостороне. Дополнительно: побайтовая идентичность двух ABI, четыре одновременные замены без `memory.grow`, четыре максимальных 256-frame банка, нормальная ошибка и восстановление после отсутствующего ROM.
- `verify-wavetable-app.html`: настоящий `index.html?engine=wavetable`, его BrowserBackend, Rack, AudioWorklet и все настоящие workers. Патч, transport и ноты задаются через публичный API приложения. Память и playbackStats опрашиваются раз в секунду; есть режим повторных полных preset edits.
- CPU: последовательные AB/BA прогоны, по два на версию/сценарий, `Core.process(128)` и `process.threadCpuUsage` Node 24.19; отдельно wall time и p99. В отдельном AB/BA сравниваются восемь повторных preset edits: полная control/preparation/render CPU, число компиляций и переданных байтов. Это разные метрики.
- PCM: 21 динамический сценарий при 44.1/48/96 kHz. Note entry/release/retrigger, Position, Voice shift, index, sync ratio, U3/U8/U4, изменение routing/mode и таблиц включены. Никаких подгонок громкости/времени или исключения переходных отсчётов. Порог: error RMS < −100 dBr и max absolute error < 1e−6.
- WAV-пара: одинаковые 3.2 s, четыре ноты, движение всех Position и release; одинаковое усиление ×16, без clipping. Численное сравнение выполняется до усиления.

Свои сборки и тесты не запускаются параллельно CPU-замерам или длительному browser playout. Другие процессы пользователя остаются работать.

Для фоновой проверки панель in-app browser скрыта; интерфейс приложения находится в закрытом disclosure. Сам browser сообщает `document.visibilityState: "visible"`; это явно записано в JSON. Данный прогон проверяет воспроизведение при скрытом интерфейсе IAB, а не Page Visibility `hidden`, sleep ОС, все мобильные браузеры или DAW. Stable 1.0 device/DAW gates остаются отдельными.

Браузер вправе округлять latency hint; в отчёте сохраняются фактические `baseLatency` и `outputLatency`, согласно [Web Audio specification](https://webaudio.github.io/web-audio-api/#dom-audiocontextoptions-latencyhint).

## Промежуточные результаты

Сохранены также неудачные попытки: `realtime-candidate3-300s.json` содержит два underrun за 300 s при прежнем `interactive` buffer; `app-candidate6-startup.json` и `app-candidate10-startup.json` показывают превышение памяти полного интерфейса. `app-cold-candidate11-600s.json`: шесть underrun / 64 ms в первые пять секунд, затем 607 s без новых пропусков при полных preset edits. `app-warm-candidate12-aborted.json` фиксирует оставшиеся два стартовых underrun до исправления resume и прогрева snapshots; прогон остановлен, полного playbackStats-отчёта нет. Эти файлы не являются финальными acceptance-результатами. `memory-candidate9.json` прошёл только бюджет, после чего отдельная проверка замены банков выявила удержание завершённого crossfade. CPU/audio файлы без суффикса ship относятся к промежуточным сборкам; hashes записаны в соответствующих JSON.
